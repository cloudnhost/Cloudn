# CloudN Agent Integration Contract

API version: `v1` (base path `/api/v1/agent`)
Audience: CloudN Panel developers integrating against the CloudN Agent.

This document is the complete, authoritative contract between the CloudN
Panel and the CloudN Agent. It is written so that the Panel can be
implemented **without inspecting Agent source code**. If something the
Panel needs isn't described here, treat it as not-yet-supported rather than
guessing at Agent internals.

---

## 1. Overview

```
CloudN Panel  <──HTTPS (REST)──>  CloudN Agent
CloudN Panel  <──WebSocket──────>  CloudN Agent   (console streaming)
Browser       <──WebSocket──────>  CloudN Agent   (console streaming, via short-lived token)
Browser/User  <──SFTP────────────>  CloudN Agent   (file access)
```

- The Agent exposes a REST API and a WebSocket console endpoint.
- The Panel is the control plane: it owns users, plans, permissions, and
  decides *what* configuration a server should have.
- The Agent is the execution plane: it owns containers, files, consoles,
  and enforces the configuration it is given. **The Agent does not make
  entitlement decisions** — if the Panel sends a resource/allocation
  config, the Agent applies it as instructed.

---

## 2. Authentication

### 2.1 Panel → Agent (all REST endpoints under `/api/v1/agent`)

Every request must include:

```
Authorization: Bearer <CLOUDN_NODE_ID>.<CLOUDN_NODE_SECRET>
```

- `CLOUDN_NODE_ID` and `CLOUDN_NODE_SECRET` are generated by the Panel when
  a node is created, and provisioned into the Agent's environment
  (`CLOUDN_NODE_ID`, `CLOUDN_NODE_SECRET`) during installation.
- The Agent compares the secret using a constant-time comparison.
- Invalid credentials return `401 UNAUTHORIZED` or `401
  INVALID_NODE_CREDENTIALS`.
- The Node Secret is never returned by any Agent endpoint, never logged,
  and should be treated as a long-lived, highly sensitive credential
  (rotate via a new install/registration if compromised).

`GET /health` is the only endpoint that does **not** require
authentication (see §11).

### 2.2 Browser → Agent (console WebSocket)

Browsers never receive the Node Secret. Instead:

1. Panel calls `POST /api/v1/agent/servers/:id/console/token` (authenticated
   as above) to obtain a short-lived (60s) session token scoped to one
   server and the `console` capability.
2. Panel hands that token to the browser client.
3. Browser opens `wss://<agent>/api/v1/agent/servers/:id/console/ws?token=<token>`.

### 2.3 SFTP

Username format: `<server-id>.<panel-username>`, password: a per-server
SFTP credential managed by the Panel. See §10.

## 3. Conventions

- All request/response bodies are JSON (`Content-Type: application/json`)
  except file upload/download (binary streams) and backup download.
- All successful responses follow:
  ```json
  { "success": true, "data": { /* ... */ } }
  ```
- All error responses follow (see §12 for full error code list):
  ```json
  { "success": false, "error": { "code": "SERVER_NOT_FOUND", "message": "Server does not exist." } }
  ```
- `serverId` in URLs is the **CloudN server UUID** (also the Agent-side
  directory name), not the Panel's internal numeric ID. The Panel's own ID
  is sent as `panelServerId` at creation time and is otherwise opaque to
  the Agent.
- Timestamps are ISO-8601 UTC strings.

## 4. Node Registration

### `POST /api/v1/agent/nodes/register`

Called by the Agent (not the Panel) on startup and on every reconnect
after an outage, to identify itself and (re)establish that it is a valid
node. Documented here because the Panel must implement the receiving side.

**Auth:** Node Bearer token (§2.1)

**Request body:**
```json
{
  "nodeId": "node_01HFX...",
  "nodeUuid": "3f1c9a2e-2222-4444-8888-abcdefabcdef",
  "publicUrl": "https://node1.example.com:8080"
}
```

**Response (200):**
```json
{ "success": true, "data": { "acknowledged": true } }
```

**Errors:** `401 INVALID_NODE_CREDENTIALS` if the node is unknown/disabled.

Behavior: the Agent retries this call indefinitely with exponential
backoff (starting at 1s, capped at 60s) if the Panel is unreachable or
returns a non-2xx status. The Agent continues serving local API/Docker
operations while disconnected — it does not crash or block on this call.

## 5. Heartbeat

### `POST /api/v1/agent/heartbeat`

Sent by the Agent every `HEARTBEAT_INTERVAL_MS` (default 15000ms).

**Auth:** Node Bearer token

**Request body:**
```json
{
  "nodeId": "node_01HFX...",
  "agentVersion": "0.1.0",
  "timestamp": "2026-08-19T12:00:00.000Z",
  "cpuUsagePercent": 34.21,
  "memoryUsageMb": 4096,
  "memoryTotalMb": 16384,
  "diskUsageMb": 51200,
  "diskTotalMb": 256000,
  "dockerStatus": "ok",
  "agentStatus": "ok",
  "runningServers": 7,
  "totalServers": 12
}
```

`dockerStatus`: `"ok" | "unavailable"`. `agentStatus`: `"ok" | "degraded"`.

**Response (200):** `{ "success": true, "data": { "acknowledged": true } }`

**Panel-side online/offline determination:** the Panel should mark a node
`OFFLINE` if no heartbeat has been received within `3 ×
HEARTBEAT_INTERVAL_MS` (default: 45s) of the last one, and `ONLINE`
otherwise. This value is configured on the Agent, so the Panel may want to
allow a per-node override or a conservative fixed default (e.g. 60s).

## 6. Agent → Panel Events

### `POST /api/v1/agent/events`

Generic event stream for anything that isn't a heartbeat. The Panel should
accept unknown event `type`s without erroring (forward-compatibility).

**Auth:** Node Bearer token

**Request body:**
```json
{
  "type": "server.install.completed",
  "data": { "serverId": "3f1c9a2e-...": "..." },
  "timestamp": "2026-08-19T12:00:00.000Z"
}
```

**Known event types:**

| type                         | data payload                                      |
|-------------------------------|----------------------------------------------------|
| `server.install.started`      | `{ serverId }`                                     |
| `server.install.output`       | `{ serverId, line }`                               |
| `server.install.completed`    | `{ serverId }`                                     |
| `server.install.failed`       | `{ serverId, reason }`                             |
| `server.status.changed`       | `{ serverId, status }` (see §7.1 for status enum)  |
| `server.resources.updated`    | `{ serverId, resources }`                          |
| `server.allocation.updated`   | `{ serverId, allocation }`                         |
| `server.deleted`              | `{ serverId }`                                     |
| `server.crashed`              | `{ serverId, exitCode, reason }`                   |
| `agent.error`                 | `{ message, context }`                             |

**Response (200):** `{ "success": true, "data": { "acknowledged": true } }`

If the Panel is unreachable, the Agent logs a warning and drops the event
rather than queuing indefinitely (heartbeats will re-sync overall status on
the next successful call).

## 7. Server Lifecycle (Panel → Agent)

All endpoints below are under `/api/v1/agent/servers` and require the Node
Bearer token.

### 7.1 Server status enum

`installing | install_failed | offline | starting | running | stopping | crashed | suspended | deleting`

### `GET /api/v1/agent/servers`
List all servers this Agent currently knows about.

**Response (200):**
```json
{ "success": true, "data": [ { "id": "...", "status": "running", "...": "..." } ] }
```

### `POST /api/v1/agent/servers`
Creates a server: allocates its directory, validates the Egg, and begins
async installation (see `CLOUDN_EGG_SPEC.md`).

**Request body:**
```json
{
  "serverId": "3f1c9a2e-2222-4444-8888-abcdefabcdef",
  "panelServerId": "1042",
  "egg": { "...": "full Egg JSON, see CLOUDN_EGG_SPEC.md" },
  "environment": { "EULA": "true" },
  "resources": {
    "cpuPercent": 200,
    "memoryMb": 4096,
    "swapMb": 0,
    "diskMb": 10240,
    "ioWeight": 500
  },
  "allocation": {
    "ip": "203.0.113.10",
    "port": 25565,
    "additionalPorts": [25566]
  }
}
```

**Response (201):** the created `ServerRecord` (see §7.7).

**Errors:** `422 VALIDATION_ERROR`, `422 EGG_INVALID`, `409
SERVER_ALREADY_EXISTS`.

### `GET /api/v1/agent/servers/:id`
Returns the current `ServerRecord`. `404 SERVER_NOT_FOUND` if unknown.

### `POST /api/v1/agent/servers/:id/start`
Creates (if needed) and starts the container. `409
SERVER_ALREADY_RUNNING`, `409 SERVER_INSTALL_IN_PROGRESS`, `423
SERVER_SUSPENDED`.

### `POST /api/v1/agent/servers/:id/stop`
Gracefully stops the container (SIGTERM, then SIGKILL after Docker's
default grace period). `409 SERVER_NOT_RUNNING`.

### `POST /api/v1/agent/servers/:id/restart`
Stops then starts. `409 SERVER_NOT_RUNNING` if there is no container yet.

### `POST /api/v1/agent/servers/:id/kill`
Force-kills the container immediately (SIGKILL). `409 SERVER_NOT_RUNNING`.

### `POST /api/v1/agent/servers/:id/suspend`
Stops the server (if running) and marks it `suspended`; further
start/console/file-write actions are blocked until unsuspended. Use this
for e.g. non-payment.

### `POST /api/v1/agent/servers/:id/unsuspend`
Clears the suspension flag; server returns to `offline`, awaiting an
explicit start.

### `DELETE /api/v1/agent/servers/:id`
Stops and removes the container, deletes the server's directory
irrecoverably (any backups the Panel wants to keep must be taken/exported
first via §9), and removes Agent-side state.

**Response (200):** `{ "success": true, "data": null }`

### `PATCH /api/v1/agent/servers/:id/resources`
Updates the resource limits the Agent enforces. Body is a `ResourceLimits`
object (§7.7). Takes effect immediately for CPU/memory on a running
container where supported by the runtime; a restart may be required for
full effect depending on the underlying Docker version.

### `PATCH /api/v1/agent/servers/:id/allocation`
Updates the network allocation. **Requires a restart** (stop + start) to
rebind container ports; the Agent does not hot-swap port bindings on a
live container.

### `POST /api/v1/agent/servers/:id/console/token`
Issues a 60-second console session token for browser WebSocket use (§2.2).

**Response (200):**
```json
{ "success": true, "data": { "token": "eyJhbGciOi...", "expiresInSeconds": 60 } }
```

### 7.7 `ServerRecord` shape

```json
{
  "id": "3f1c9a2e-2222-4444-8888-abcdefabcdef",
  "panelServerId": "1042",
  "status": "running",
  "containerId": "a1b2c3...",
  "egg": { "...": "..." },
  "environment": { "EULA": "true" },
  "resources": { "cpuPercent": 200, "memoryMb": 4096, "swapMb": 0, "diskMb": 10240, "ioWeight": 500 },
  "allocation": { "ip": "203.0.113.10", "port": 25565, "additionalPorts": [25566] },
  "createdAt": "2026-08-19T12:00:00.000Z",
  "updatedAt": "2026-08-19T12:05:00.000Z",
  "suspended": false
}
```

## 8. Console & Logs

### WebSocket `GET /api/v1/agent/servers/:id/console/ws?token=<token>`

Auth via short-lived token from §7's `console/token` endpoint. See §2.2.

**Agent → client messages:**
```json
{ "event": "console_output", "data": "Server thread/INFO]: Done!\n" }
{ "event": "status", "data": "running" }
{ "event": "error", "data": "Failed to attach to container output" }
```

**Client → Agent messages:**
```json
{ "event": "send_command", "data": "say hello world" }
```

### `GET /api/v1/agent/servers/:id/logs?tail=200`
Returns recent buffered stdout/stderr as a single string (fallback for
clients not using the WebSocket, or for the Panel's own display).

**Response (200):** `{ "success": true, "data": { "logs": "..." } }`

### `GET /api/v1/agent/servers/:id/stats`
Point-in-time resource usage (raw Docker stats passthrough): CPU, memory,
network, block IO counters.

## 9. File Management

Base path: `/api/v1/agent/servers/:id/files`. All paths are relative to the
server's root directory; the Agent rejects any path that would escape it
(`400 INVALID_PATH`).

| Method & Path                | Body / Query                          | Description                          |
|-------------------------------|----------------------------------------|----------------------------------------|
| `GET /list?path=/`            | —                                       | List directory contents.               |
| `GET /contents?path=..`       | —                                       | Read a text file's contents.           |
| `PUT /contents?path=..`       | `{ "content": "..." }`                  | Overwrite/create a file.               |
| `POST /directory`             | `{ "path": ".." }`                      | Create a directory (recursive).        |
| `POST /rename`                | `{ "from": "..", "to": ".." }`          | Rename/move.                           |
| `POST /copy`                  | `{ "from": "..", "to": ".." }`          | Copy a file or directory.              |
| `DELETE /`                    | `{ "path": ".." }`                      | Delete a file or directory (recursive).|
| `GET /download?path=..`       | —                                       | Stream a file for download.            |
| `POST /upload?path=..`        | raw binary body                         | Stream-upload a file.                  |

`list` response entries:
```json
{ "name": "server.jar", "path": "/server.jar", "isDirectory": false, "size": 41823921, "modifiedAt": "2026-08-19T12:00:00.000Z", "mode": "644" }
```

**Errors:** `404 FILE_NOT_FOUND`, `400 INVALID_PATH`, `413
FILE_TOO_LARGE` (read endpoint caps at 10MB by default; use
`download` for larger files).

## 10. SFTP

The Agent runs a real SFTP server (default port `2022`, configurable via
`SFTP_PORT`).

| Property              | Value                                                             |
|------------------------|----------------------------------------------------------------------|
| Host                   | The node's public IP/hostname (same as the Agent's host)             |
| Port                   | `SFTP_PORT` (default `2022`)                                          |
| Username format        | `<server-id>.<panel-username>`                                       |
| Authentication         | Password — a per-server SFTP credential the Panel generates and displays to the user |
| Directory restriction  | Chrooted to that server's directory only; identical isolation guarantee as the File API |

The Agent does not generate or store the authoritative SFTP password — the
Panel is expected to provision it and the Agent's authenticator validates
it (directly or via a callback to the Panel, deployment-dependent). The
Panel is responsible for displaying host/port/username/password to the
end user.

## 11. Health

### `GET /health` — **unauthenticated**
Minimal public status, safe to expose to load balancers/uptime checks.
```json
{ "status": "ok", "dockerConnected": true, "panelConnectivity": "connected" }
```

### `GET /api/v1/agent/status` — authenticated
Full diagnostic snapshot: same fields as the heartbeat payload plus
redacted config (no secrets).

## 12. Backups

Base path: `/api/v1/agent/servers/:id/backups`.

| Method & Path                     | Description                              |
|-------------------------------------|---------------------------------------------|
| `GET /`                             | List backups for a server.                   |
| `POST /`                            | Create a new backup (tar.gz of server dir).  |
| `GET /:backupId/download`           | Stream the backup archive.                   |
| `POST /:backupId/restore`           | Extract a backup over the server directory.  |
| `DELETE /:backupId`                 | Delete a backup.                             |

Backup record shape:
```json
{ "id": "b7e2...", "serverId": "3f1c9a2e-...", "fileName": "b7e2....tar.gz", "sizeBytes": 10485760, "createdAt": "2026-08-19T12:00:00.000Z" }
```

**Errors:** `404 BACKUP_NOT_FOUND`, `500 BACKUP_FAILED`.

---

## 13. Networking / Allocations

The Panel owns allocation assignment rules (which IP:port belongs to which
server/user, port pool management, etc). The Agent only executes what it's
told:

- `allocation.ip` / `allocation.port` (+ optional `additionalPorts`) are
  supplied at server creation (§7) and updated via `PATCH
  .../allocation` (§7).
- The Agent binds these as Docker port mappings on the server's container,
  host-ip-scoped to the given IP.
- The Agent performs no allocation bookkeeping of its own and never
  invents or reassigns allocations.

## 14. Error Codes

Consistent envelope on every error:
```json
{ "success": false, "error": { "code": "SERVER_NOT_FOUND", "message": "Server does not exist.", "details": {} } }
```

| Code                          | HTTP Status | Meaning                                         |
|---------------------------------|-------------|---------------------------------------------------|
| `UNAUTHORIZED`                  | 401         | Missing/malformed Authorization header             |
| `INVALID_NODE_CREDENTIALS`      | 401         | Node ID/secret mismatch                            |
| `TOKEN_EXPIRED`                 | 401         | Console session token invalid/expired               |
| `FORBIDDEN`                     | 403         | Authenticated but not permitted                     |
| `VALIDATION_ERROR`              | 422         | Request body failed schema validation               |
| `INVALID_PATH`                  | 400         | File path escapes server root or is malformed        |
| `SERVER_NOT_FOUND`              | 404         | No such server                                       |
| `SERVER_ALREADY_EXISTS`         | 409         | `serverId` already in use                            |
| `SERVER_ALREADY_RUNNING`        | 409         | Start requested on a running server                  |
| `SERVER_NOT_RUNNING`            | 409         | Stop/restart/kill on a non-running server             |
| `SERVER_SUSPENDED`              | 423         | Action blocked because server is suspended            |
| `SERVER_INSTALL_IN_PROGRESS`    | 409         | Start requested while installing                      |
| `DOCKER_UNAVAILABLE`            | 503         | Agent cannot reach the Docker daemon                  |
| `DOCKER_OPERATION_FAILED`       | 502         | Docker Engine API call failed                         |
| `CONTAINER_NOT_FOUND`           | 404         | Referenced container no longer exists                 |
| `FILE_NOT_FOUND`                | 404         | File/directory does not exist                         |
| `FILE_TOO_LARGE`                | 413         | File exceeds readable/upload size limit                |
| `DISK_LIMIT_EXCEEDED`           | 507         | Server's disk quota exhausted                          |
| `FILE_OPERATION_FAILED`         | 500         | Unclassified filesystem error                          |
| `EGG_INVALID`                   | 422         | Egg definition failed spec validation                  |
| `EGG_INSTALL_FAILED`            | 500         | Install script/container failed                        |
| `ALLOCATION_INVALID`            | 422         | Allocation payload malformed                            |
| `BACKUP_NOT_FOUND`              | 404         | Referenced backup does not exist                        |
| `BACKUP_FAILED`                 | 500         | Backup create/restore/delete failed                     |
| `INTERNAL_ERROR`                | 500         | Unclassified server error                                |
| `NOT_IMPLEMENTED`               | 501         | Endpoint recognized but not yet implemented              |
| `RATE_LIMITED`                  | 429         | Too many requests from this node in the current window   |

## 15. Rate Limiting

All authenticated endpoints are subject to a per-node rate limit
(`RATE_LIMIT_PER_MINUTE`, default 600/min). Exceeding it returns `429
RATE_LIMITED` with standard `RateLimit-*` headers.

---

## 16. Versioning Policy

- Breaking changes bump the path prefix (`/api/v1/agent` → `/api/v2/agent`)
  and are documented as a new section here before the Agent is upgraded.
- Additive, backward-compatible changes (new optional fields, new event
  types, new endpoints) do not bump the version; Panel implementations
  should ignore unknown fields/event types defensively.
